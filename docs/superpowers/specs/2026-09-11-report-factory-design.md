# Фабрика учебных отчётов

Дата: 2026-09-11  
Статус: согласованный дизайн, ждать ревью перед планом реализации

## Цель

Grok в этом репозитории по одному запросу (`/report` или «сделай отчёт») превращает PDF задания в готовый `.docx` отчёт по дисциплине: читает задание, выполняет работу (код, браузер, терминал, иногда диаграммы), сохраняет скриншоты, собирает Word **правкой копии эталона**, а не генерацией документа с нуля.

## Не цели

- Писать Word через Composio / HTML-to-Word / Google Docs. Composio можно использовать только чтобы залить уже готовый локальный `.docx` в облако, если пользователь явно попросит.
- Восстанавливать оформление списком правил (шрифт 14, отступ 1.25 см и т.п.) и собирать новый `Document()`.
- Генерировать титульник с нуля.
- Рисовать технические диаграммы нейросетью, если их можно собрать кодом (Mermaid).
- Делать универсальную СДО / веб-UI. Это CLI + скиллы Grok внутри репозитория.

## Инварианты

1. `subjects/<предмет>/sample.docx` — только чтение. Любая работа стартует с **копии** в подпапку работы.
2. Оформление = то, что уже лежит в XML эталона. Новые абзацы, таблицы и рисунки — клоны существующих блоков этого файла, не новые стили.
3. Ни один PNG (скрин, диаграмма, картинка из PDF, если идёт в отчёт) не попадает в `.docx`, пока модель не открыла файл и не подтвердила, что он годится.
4. После сборки страницы `report.docx` рендерятся в PNG, модель смотрит **все** страницы. Пока verify не пройден, отчёт не готов.
5. Нет совпадения строки на титульнике → стоп, без похожих замен и без нового титульника.

## Конфиги

### `student.yaml` (корень)

```yaml
full_name: "Иванов Иван Иванович"
name_short: "Иванов И.И."
group: "ИКБО-21-23"
faculty: ""
university: ""
city: ""
year: 2026
```

Пустые строки не подставляются (поле титульника не трогаем, если в `title-fields` нет `find` для него).

### `subjects/<предмет>/title-fields.yaml`

Привязан к **тексту эталона**, не к предыдущей лабе. Каждая новая работа копирует эталон, поэтому `find` всегда ищется в свежей копии.

```yaml
fields:
  student_name:
    find: "Петров Пётр Петрович"
    to: student.full_name
  group:
    find: "ИКБО-00-00"
    to: student.group
  topic:
    find: "Лабораторная работа №1. Пример"
    to: work.title
body_start:
  type: heading_text   # heading_text | paragraph_index | section
  value: "Цель работы"
figure_caption: "Рисунок {n} – {caption}"
table_caption: "Таблица {n} – {caption}"
confirmed: true
```

`to: student.*` берётся из `student.yaml`. `to: work.title` — из `work.yaml` этой подпапки.

Файл привязан к эталону, несмотря на имя: в нём же граница тела и шаблоны подписей, чтобы не плодить второй конфиг предмета.

Первичное заполнение: при заведении предмета Grok рендерит 1-ю страницу эталона, читает титульник, предлагает `find`-строки, `body_start` и шаблоны подписей по живым примерам в эталоне. Пользователь подтверждает — тогда ставится `confirmed: true`. Compose не запускается, если файла нет или `confirmed` не `true`.

### `work.yaml` (в папке работы)

```yaml
title: "Лабораторная работа №3. Процессы"
number: 3
subject: os
```

Grok заполняет из `assignment.md` до `patch_title`.

### `screenshots/manifest.json`

```json
[
  {
    "file": "01-install.png",
    "caption": "Установка зависимостей",
    "source": "terminal",
    "ok": true
  }
]
```

`source`: `browser` | `terminal` | `ide` | `diagram` | `other`.  
`ok: true` только после визуального осмотра моделью. Compose игнорирует записи с `ok: false` и падает, если на диск клали файл, а `ok` так и не стал `true`, при том что `report.md` на него ссылается.

## Фазы `/report`

### 0. Старт

- Есть `student.yaml`, иначе стоп.
- Предмет: из аргумента, из cwd внутри `subjects/<slug>/...`, или спросить один раз.
- Нет `sample.docx` → стоп, нужен эталон другой работы по этой дисциплине.
- Нет `title-fields.yaml` → фаза заведения предмета (рендер титульника, черновик полей, ждать подтверждения), не выполнение лабы.
- Создать `lab-NN-slug/` если нет. Скопировать `sample.docx` → `lab-NN-slug/report.docx`. Эталон не открывать на запись.
- Положить/найти `assignment.pdf` в папке работы.

Повторный запуск на существующей папке **не** затирает `work/`, `screenshots/`, `report.md`. `report.docx` можно сбросить новой копией эталона только по явной команде «пересобрать с эталона» (после порчи копии).

### 1. Ingest

`python tools/pdf_to_md.py <assignment.pdf> --out <папка работы>`

- Движок по умолчанию: **pymupdf4llm**, картинки на диск, в Markdown в порядке чтения.
- Если текста почти нет (скан) — Marker, если установлен. Иначе стоп с текстом «нужен текстовый PDF или Marker».
- Выход: `assignment.md`, `images/`.
- Если объектов-картинок в PDF больше, чем файлов в `images/` — предупреждение в stdout; Grok не выдумывает недостающие рисунки задания.

Grok дальше читает `assignment.md`, не PDF, кроме сверки пропавших картинок.

### 2. Execute

- Разобрать задание, сделать работу в `work/` (код, команды, браузер через chrome-devtools).
- Скриншоты: `tools/screenshot.py` → `screenshots/NN-slug.png` + запись в манифест с `ok: false`.
- Диаграммы: исходник `work/diagrams/<name>.mmd` → `tools/diagram.py` → PNG рядом. Не использовать image generation для блок-схем, последовательностей, архитектур, если хватает Mermaid.
- Модель **открывает каждый PNG** (чтение файла изображения). Критерии: то окно/вывод, что просит задание; текст читаем; нет обрезки важного; диаграмма без наложений подписей. Не ок — переснять/править mermaid, не ставить `ok: true`.
- Пишет `report.md`: те же разделы, что в эталоне (цель, ход, результаты, выводы — по факту эталона). Рисунки — markdown-картинки на проверенные PNG. Таблицы — GFM. Код — fenced blocks.

Конвенция в `report.md` для подписи, которую потом перенесёт сборщик:

```markdown
![Установка зависимостей](screenshots/01-install.png)
```

Alt = текст подписи без префикса «Рисунок N». Префикс и номер берёт сборщик из клона подписи эталона.

Таблица с названием — строка сразу перед таблицей:

```markdown
Таблица: Результаты измерений

| Параметр | Значение |
| --- | --- |
```

### 3. Compose

Только правка `lab-NN/report.docx` (копии).

1. `patch_title.py` — для каждого `fields.*.find` точная замена на вычисленный `to`. Нет вхождения → exit ≠ 0, файл не сохраняется с частичными заменами (атомарно: работа на temp, успех → replace).
2. Тело после титульника очищается. Граница задаётся при заведении предмета и пишется в `title-fields.yaml` как `body_start` (см. конфиги). Порядок определения: section break, если он есть и пользователь его подтвердил; иначе текст/индекс первого абзаца тела (обычно первый заголовок вроде «Цель работы»). Без подтверждённого `body_start` compose не стартует. Эталон не обязан содержать section break.
3. `replace_body.py` читает `report.md` и вставляет блоки, клонируя из **этого же** docx прототипы:
   - абзац стиля Normal (или фактический стиль тела эталона)
   - Heading 1/2/3 если такие есть
   - пара «drawing + абзац подписи» для рисунка
   - таблица (границы, шапка, ячейки) + абзац названия таблицы
   - блок кода, если в эталоне есть пример моноширинного абзаца; если нет — абзац тела с моноширинным run, только в этом случае допускается точечный rFonts на run, без смены стилей документа
4. Картинка вставляется в клон drawing: файл в `word/media/`, relationship, размеры с сохранением aspect ratio, ширина не больше ширины области текста эталона.
5. Нумерация подписей: пересчитать по порядку вставки. Строка собирается по `figure_caption` / `table_caption` из `title-fields.yaml` (шаблон снят с живой подписи эталона при онбординге).

Если в эталоне нет ни одного рисунка, а `report.md` требует рисунок — стоп (эталон обязан содержать живой пример нужного типа блока). То же для таблиц. Если в предмете таблиц не бывает и в MD их нет — не требовать.

### 4. Verify

`render_docx.py` → `lab-NN/preview/page-01.png`, …

Рендер: на Windows сначала автоматизация установленного Word (то, чем откроет преподаватель); если Word нет — LibreOffice. Нет ни того ни другого → verify провален, отчёт не готов.

Модель смотрит все PNG preview:

- титульник: сетка/герб/таблица на месте, ФИО и тема новые, ничего не уехало
- поля, абзацы, заголовки визуально как в эталоне
- каждый рисунок: не обрезан, не растянут, подпись под ним, номер подряд, содержание совпадает с заданием
- таблицы: сетка целая, заголовок таблицы на месте

Брак → правка той же копии (не эталона) → снова рендер. После трёх неудачных verify — стоп и список дефектов пользователю, не объявлять готовым.

Готовый артефакт: `subjects/<предмет>/lab-NN-<slug>/report.docx`.

## Скрипты (`tools/`)

| Скрипт | Вход | Выход / код |
|---|---|---|
| `pdf_to_md.py` | PDF, `--out` | `assignment.md`, `images/`; ≠0 если пустой текст и нет fallback |
| `new_work.py` | subject, slug, pdf | создаёт папку, копирует sample → report.docx; ≠0 если нет эталона |
| `patch_title.py` | report.docx, title-fields.yaml, student.yaml, work.yaml | атомарная замена find→to |
| `replace_body.py` | report.docx, report.md, manifest, caption templates | тело из клонов |
| `insert_figure.py` | docx, png, caption, n | клон блока рисунка (используется из replace_body) |
| `screenshot.py` | `--source`, `--caption`, `--out-dir` | PNG + строка манифеста `ok: false` |
| `diagram.py` | `.mmd` | PNG |
| `render_docx.py` | docx, `--out-dir` | `page-NN.png` |
| `paths.py` (библиотека, не CLI) | путь | `assert_not_sample()` — отказ, если resolved path это `subjects/*/sample.docx` |

Общий CLI-стиль: argparse, UTF-8, код 0 только при полном успехе, ошибки в stderr на русском или английском — единообразно **на русском**.

Запись в `sample.docx` блокируется сравнением resolved path с `subjects/*/sample.docx`.

## Скиллы Grok

Проектные, в `.grok/skills/`.

- `report` — пользовательский вход. Фазы 0–4 по этому документу. Триггеры: `/report`, «сделай отчёт», «лабораторная», PDF задания + эталон.
- `pdf-to-md` — только конвертация, вызывается из `report`.
- `build-report` — compose + verify, вызывается из `report`, когда execute уже сделан.

`AGENTS.md` в корне: эталон read-only; не собирать docx с нуля; не пропускать визуальный осмотр PNG; не ходить в Composio за Word.

## Ошибки

| Ситуация | Поведение |
|---|---|
| Нет student.yaml / sample.docx / PDF | Стоп, что именно положить |
| title-fields не подтверждены | Только онбординг предмета |
| find на титульнике не найден | exit ≠ 0, копия без частичных замен |
| Скан-PDF без Marker | Стоп |
| PNG без `ok: true`, но на него ссылается report.md | compose не стартует |
| Нет прототипа блока в эталоне | Стоп, эталон неполный для этого типа |
| Нет Word и нет LibreOffice | verify провален |
| Попытка save в sample.docx | отказ |

Сломанный `report.docx` чинится новой копией эталона по явной команде, не правкой эталона.

## Тесты

Фикстуры в `tests/fixtures/`. Не требуют Grok.

1. PDF с двумя картинками в известном порядке → MD со ссылками в том же порядке, оба файла на диске.
2. `new_work` копирует эталон; SHA256 `sample.docx` до и после совпадает.
3. `patch_title` меняет ФИО; заведомо отсутствующий `find` → ≠0, содержимое docx как до вызова.
4. Эталон с одним рисунком → вставка второго через клон: две подписи по шаблону эталона, `word/media` содержит оба изображения.
5. `render_docx` на фикстуре даёт хотя бы один непустой PNG (тест skip, если нет ни Word, ни LibreOffice).

Приёмка пайплайна (ручная, первая живая лаба): реальный PDF + эталон, пользователь смотрит титульник и страницы с рисунками.

## Критерий готовности системы

Можно в чате Grok из корня репо: положить эталон, подтвердить title-fields, кинуть PDF, написать `/report` — и в подпапке работы лежит `report.docx`, прошедший render-осмотр, титульник эталона с подставленными ФИО/темой, тело с проверенными скриншотами.
